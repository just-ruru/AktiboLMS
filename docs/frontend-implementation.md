## Backend contract and data integrity

### Confirmed profile contract

The backend-only branch exposes student profile operations by explicit ID:

- `GET /api/students/{id}`
- `PUT /api/students/{id}`

The frontend `Profile` shape currently follows the backend response fields: `id`, `studentId`, `firstName`, `lastName`, `email`, optional nullable `description`, `active`, `createdAt`, and `updatedAt`.

- The boolean is serialized as `active`, not `isActive`: the Spring service exposes an `isActive()` getter and Jackson writes the property name `active`. The frontend interface was corrected to match the wire format rather than translating it, so `frontend/src/lib/backendAdapter.ts` declares `active: boolean` and `frontend/tests/register.spec.ts` mocks `active: true`.

No current-user/session endpoint was found in the initial backend review. Do not guess a student ID to load a real user's profile. The profile page should remain empty/unavailable without an authorized identity mechanism.

### Temporary profile fixture

- Toggle: `VITE_ENABLE_MOCK_DATA` in `frontend/.env.local`.
- The checked-in example, `frontend/.env.example`, sets it to `false`.
- The local ignored `.env.local` currently enables test data (`true`) for local UI review.
- Disable the fixture by setting the value to `false` or removing it, then restart Vite. The Account Profile screen displays a visible test-data banner while the fixture is active.
- The fixture contains only clearly labeled invalid/test values; it must never be represented as production data.

### Confirmed registration, course, and authentication contracts

The backend-only branch exposes student creation:

- `POST /api/students` accepts `StudentRequest`: required `studentId`, `firstName`, `lastName`, `email`, `password`; optional `description`.
- Success is HTTP `201` with `StudentResponse` (password omitted). Duplicate email/student ID may return `400` or `409`; validation returns `400` with a field-to-message `details` map.
- The backend hashes the submitted password with BCrypt before storage.
- The backend does not accept `phone` or `courseId` on student creation. There is no course-enrollment endpoint evidenced, so the Registration screen must not imply that course selection will be saved. `GET /api/courses` lists paginated, non-archived catalog courses and is not a registration/enrollment contract.
- No dedicated login/authentication/JWT endpoint exists. Student creation does not establish a frontend login session. Password reset, email verification, role assignment, and support submission contracts remain unconfirmed.
- Backend local base URL documented by its README is `http://localhost:8080`; CORS allows `http://localhost:5173` for `/api/**`. Keep the base URL configurable through frontend environment configuration, not embedded in page code.

Until the relevant endpoint is confirmed, screens must not claim successful authentication, email delivery, role assignment, password change, enrollment, or support submission. Registration may call the confirmed student-creation endpoint but must state accurately that login/email verification are not available.

### Confirmed instructor contract

The backend-only branch exposes instructor CRUD: `POST /api/instructors`, `GET /api/instructors/{id}`, `GET /api/instructors`, `PUT /api/instructors/{id}`, and `DELETE /api/instructors/{id}`.

- `InstructorRequest` mirrors `StudentRequest`: required `instructorId`, `firstName`, `lastName`, `email`, `password` (6–255 characters); optional `description`. The update service re-hashes the password when one is supplied and returns `400` for duplicates, `404` for an unknown or inactive record.
- Every endpoint is keyed by an explicit record ID and no current-user/session endpoint supplies one, so the Instructor Account Profile screen still cannot load or save an instructor. It now says so accurately — it is not connected because there is no signed-in instructor record, **not** because an instructor service is missing. An earlier revision of this tracker and the screen copy claimed the instructor endpoints did not exist; that was wrong and is corrected here.
- No instructor registration screen exists in the Figma inventory yet, so a pricing or role call-to-action for instructors routes to the role-selection screen rather than to an unimplemented form.

### Confirmed course, module, and assignment contracts

The backend-only branch exposes the course catalogue and its module tree. These are the only learning-content endpoints that exist, so they are the only content the student and instructor screens are allowed to bind to.

- `GET /api/courses` returns a Spring `Page`, so the JSON body is `{ "content": [...], "pageable": ..., "totalElements": ... }`. The frontend adapter unwraps `content`; list endpoints accept `page`, `size`, and `sort` query parameters.
- `GET /api/courses/{id}`, `POST /api/courses`, `PUT /api/courses/{id}`, `DELETE /api/courses/{id}` cover single-course reads and writes.
- `CourseRequest` is `{ courseCode, courseTitle, description, units, status }` with `units` validated positive and `status` restricted to `DRAFT`, `PUBLISHED`, `ARCHIVED`.
- `GET /api/courses/{courseId}/modules`, `POST /api/courses/{courseId}/modules`, `PUT /api/courses/{courseId}/modules/{moduleId}`, `DELETE /api/courses/{courseId}/modules/{moduleId}` cover the module tree of one course.
- `CourseModuleRequest` is `{ moduleTitle, sequenceOrder, published }` with `sequenceOrder` validated positive. Responses carry the booleans `published` and `archived` (not `isPublished`/`isArchived`).
- `GET /api/courses/assignments`, `POST /api/courses/assignments`, `DELETE /api/courses/assignments` manage instructor-to-course assignments. `CourseAssignmentRequest` is `{ instructorId, semester, academicYear, role }`.
- `frontend/src/lib/backendAdapter.ts` implements all of the above: `getCourses`, `getCourse`, `createCourse`, `updateCourse`, `deleteCourse`, `getCourseModules`, `createCourseModule`, `updateCourseModule`, `deleteCourseModule`, `getCourseAssignments`, `assignCourse`, `removeCourseAssignment`. Each returns the confirmed DTO and raises `BackendRequestError` (with `.status` and a field→message `.fieldErrors` map) for a `4xx` response.
- The adapter's local fixture is still behind `VITE_ENABLE_MOCK_DATA` and contains only two clearly labelled sample courses (`DEMO-101`, `DEMO-102`) and their two sample modules.

**Still absent from the backend**, and therefore unavailable to every screen in this branch: authentication/login/JWT, session or current-user endpoints, password reset, email verification, email sending, support tickets, enrollment, lessons, multimedia content, practice/quiz questions, feedback, module completion, learning progress, subjects or categories, learner rosters, analytics, and notifications. Screens for those areas render an explicit neutral state that says what is not connected, and never present the Figma sample content as a real record.

### Confirmed profile update contract

`PUT /api/students/{id}` mirrors the creation payload (`StudentRequest`): `studentId`, `firstName`, `lastName`, `email`, and `password` are required, `description` is optional.

- The request ID is the student's numeric record ID, which the frontend cannot obtain yet because no current-user/session endpoint exists. The adapter (`frontend/src/lib/backendAdapter.ts`) implements the confirmed request shape — it sends the record's `studentId` and `description` unchanged so an edit never erases them — but the live call stays unreachable until an identity source exists.
- `password` is validated as required (`@NotBlank`) even though the service only re-hashes it when a value is present. A profile update therefore has to carry a password, so the Edit profile screen collects one instead of pretending a save is possible. The service stores the submitted password again, so the screen asks for the current password.
- The service returns `400` for validation failures and duplicate email/student ID, and `404` for an unknown or inactive record. Duplicate email is the realistic conflict for this screen.
- The backend exposes no field for a phone number, date of birth, gender, or a separate display name. The Edit profile screen renders those four as unavailable rather than saving values the service would drop.

### Confirmed password change contract

There is no dedicated password endpoint, no session/current-user endpoint, and no password-reset flow. The only confirmed write path for a password is `PUT /api/students/{id}`, whose `password` field replaces the stored hash (`@NotBlank`, `@Size(min = 6, max = 255)`).

- `frontend/src/lib/backendAdapter.ts` exposes `changePassword(profile, newPassword)`, which sends the confirmed PUT with the record's unchanged `studentId`, `firstName`, `lastName`, `email`, and `description` and the new password in `password`.
- The current password is deliberately **not** part of that call: the endpoint has no field for it, so sending it would expose a credential for nothing. It stays in the browser, where the screen only uses it to confirm the new password differs from the typed one.
- The service does not verify the current password, and it re-hashes whatever it receives. The Security screen therefore states plainly that the current password is not sent and not verified, rather than claiming the old password was checked.
- Because there is no current-user endpoint, the live call is unreachable: `getProfile()` returns nothing without the local fixture, so the screen reports that password changes are unavailable instead of guessing a student ID. The same gap means the live request shape cannot be exercised by the browser suite yet — the mock branch is what the tests cover.
- The screen asks for at least 8 characters (the frame's guidance) while the service accepts 6; the stricter client rule is safe and documented.

## Shared components and current caveats

- `frontend/src/components/ui/Navbar.tsx` and `SiteFooter.tsx` are shared across auth/account views. Login work aligned their desktop frame contribution to the Figma login composition. The navbar now accepts `activePath` (override the highlighted nav item for screens that belong to another flow, e.g. the role screen in the sign-in flow) and `accountPath` (destination of the `MY ACCOUNT` item); the `MY ACCOUNT` item renders `aria-current="page"` and its full-width gold indicator only while it is the active route, so it stays marked on nested account screens such as `/account-profile/edit`.
- `frontend/src/components/ui/SiteFooter.tsx` accepts `accountLabel` and `accountPath`; signed-out pages keep the `Log in` item while signed-in account screens show `My account`, matching frames `92:49` and `174:450`.
- `frontend/src/components/account/AccountSidebar.tsx` is the shared account navigation sidebar (ACCOUNT OVERVIEW / EDIT PROFILE / PASSWORD & SECURITY / HELP & SUPPORT) with the active section marked `aria-current="page"`.
- `frontend/src/lib/backendAdapter.ts` covers profile read/update, password change through the confirmed update endpoint, confirmed student creation, the confirmed course / course-module / course-assignment endpoints, and the environment-gated local fixture. It does not implement authentication/session, password reset, email verification, email sending, support submission, enrollment, lessons, practice, or progress — none of those endpoints exist in the backend-only branch.
- `frontend/src/components/overlays/` holds the three reusable overlay components. Each takes its copy from props rather than hardcoding sample content, so the same component can serve any owning screen without presenting invented records.
- `frontend/tests/support/viewport.ts` is the shared responsive helper. `assertNoOverflow(page)` waits for `document.fonts.ready` before measuring, because the Google Fonts stylesheet uses `display=swap`: measuring during the font swap reports a transient overflow that is not present in the settled layout.
- `frontend/scripts/capture-screenshots.mjs` (`npm run screenshots`) captures one desktop screenshot per implemented frame into `frontend/docs/screenshots/`, including the three overlays. It expects the dev server on `http://127.0.0.1:5173` and fails the run if any screen logs a console or page error.
- Registration uses blank controlled values, validates password confirmation, posts only confirmed `StudentRequest` fields, maps backend validation/duplicate errors, and reports profile creation only after HTTP 201. Course and phone are omitted because the backend cannot persist them. After a confirmed HTTP 201 the screen also offers a `CONTINUE TO VERIFICATION PREVIEW` link that carries the address the service returned into `/verify-email`.
- Every route in `frontend/src/App.tsx` now resolves to an implemented screen, and a catch-all `*` renders `frontend/src/pages/NotFound.tsx`, so a mistyped or stale address lands on a designed screen instead of a blank page. The navbar and footer `COURSES` item points at `/courses`, the student catalogue.
- Motion: the shared utility classes are `animate-page-fade` (page wrapper), `animate-fade-in-up` (main card), plus `animate-fade-in`, `animate-slide-down`, and `animate-lift-up`. `frontend/src/index.css` disables every animation under `prefers-reduced-motion: reduce`, which is also what makes the geometry assertions in the browser suite stable — the suite emulates reduced motion before measuring.
- Line height: headings and body copy that can wrap use a normal leading (`leading-[1.5]` or `leading-[1.35]`). `leading-[0]` was removed from the course-card titles and the lesson sidebars because a wrapped line under zero leading is drawn on top of the previous line — the course title "Sample course for UI testing" and the lesson sidebar labels were visibly overlapping before the fix.
- Lint status: `npm run lint` is clean. The long-standing `react(set-state-in-effect)` warning in `frontend/src/pages/AccountProfile.tsx` was removed by loading the profile through a promise callback (`loadProfile().then(onFulfilled, onRejected)`) instead of setting state on the effect's synchronous path.
